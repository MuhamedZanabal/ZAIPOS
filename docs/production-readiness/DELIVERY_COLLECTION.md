# Delivery collection authority

Delivery creation continues to use checkout_sale_v2. Collection uses collect_delivery_payment_v2 and never accepts a client amount. Only branch-authorized cashiers/managers or the active assigned courier can collect. The receiving open cash session must be selected explicitly and belong to the same tenant and branch. Confirm only when the funds are actually received and accountable to that register; this is not a courier cash-in-transit/remittance subsystem. Electronic payment confirmation is manual provider verification, not a payment-provider integration.

The transaction locks the order, sale and receiving session; rejects existing legacy payments for reconciliation; records one immutable collection operation; creates the merchandise payment; updates the exact register method total; marks delivery complete; and writes audit evidence. The same actor and identical operation payload return the original ID, including after the receiving session closes. Changed payloads or a new operation for an already collected order fail. Current authorization is checked before replay. Direct delivery/collection mutations and the legacy collection RPC are revoked.

Merchandise payment equals the historical sale total. The separately persisted delivery fee is preserved in delivery_collections.fee_amount_fils; collected_fils is their exact sum. This does not rewrite historical sale VAT or pretend the fee is included in merchandise reports. Register receipts include the entire amount. Fee VAT classification, fee refund/credit procedures and aggregate fee reporting remain unresolved P1 work; this change is not certification of complete delivery accounting. Existing collection/payment inconsistencies must be reviewed individually, not silently repaired or recollected. Cancellation requires the authoritative sale to have been voided first.

The courier screen reads an authorized server projection, displays exact integer-fils strings, identifies the receiving register and submits one deterministic operation identity per order. Its list is explicitly limited to the latest 100 visible orders; displayed counters are not all-history business reports. If a response is lost, refresh first: a committed order is delivered with persisted collection evidence. Retrying the identical selection returns the same collection. Never change method/register merely to bypass an ambiguous result.
