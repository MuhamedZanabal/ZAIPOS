# Native manager authorization

Settings, kiosk changes, update download and update installation require current online manager authorization in the Electron main process. The renderer supplies its short-lived Supabase access token and selected tenant/branch context. Renderer role flags are never accepted as authority. Main connects only to its build-configured HTTPS Supabase endpoint, rejects redirects, bounds the request and enforces a ten-second timeout. Tokens are not persisted or logged by the native verifier.

The server RPC checks owner/admin/manager branch authorization, active branch, banned/deleted Auth users and inactive employee evidence. It rejects cashier, wrong-branch and cross-tenant users. Every request binds a fresh main-generated nonce, action and SHA-256 of the requested payload. Main verifies the complete binding before allowing the local effect. No cached permission or offline bypass exists. Network failure, bad credentials, unexpected response or missing build configuration denies the action. Ordinary checkout/printing remains subject to its existing boundaries; an unavailable network does not disable selling merely because settings cannot be changed.

An immutable database audit entry means authorization was granted, not that a local operation completed. Native structured logs record successful handler completion with the authorization ID. A crash between authorization and the local effect may leave an authorization without a completion record; do not infer application state from authorization alone. Device settings are local global settings for the terminal; this does not create cryptographic device enrollment or convert the existing renderer device UUID into a hardware-bound identity. Device revocation enforcement for offline/native operation requires a separate enrolled-device architecture review.

The UI obtains fresh session context and reports authorization failures. A cashier must sign in with an authorized manager account to change these settings. Hardware setup during a total network outage requires restoring connectivity or an independently governed operating-system support procedure; there is no application convenience bypass. Changing a database role takes effect on the next native authorization request. Approval is checked per request, not retained as a long-lived native manager session.

## Verification

Six native boundary tests fail against the former sender-only behavior and pass with the verifier. They cover missing identity, 401/403/500 responses, stale nonce/payload and successful bound authorization before effects. PostgreSQL contract tests cover branch and tenant isolation, cashier denial, supported actions, anonymous execute denial, malformed payload digest, audit evidence and revoked manager denial. Production build/Windows CI must pass on the final integrated head.

Operator smoke test: as cashier, attempt settings/kiosk/update changes and verify rejection without state change. Sign in as a same-branch manager and verify a change plus its authorization/completion evidence. Repeat with another-branch manager, revoked role, offline network and a closed/archived branch. Verify failure messages contain neither access tokens nor raw server diagnostics. Physical device identity and administrator-level local tampering remain explicit external trust boundaries, not proven by these tests.

Deployment order: back up first, ensure the managed Supabase Auth service has applied its lifecycle migrations (including deleted_at and banned_until), apply ZAIPOS migrations, then upgrade the desktop. The postgres-only CI image does not run GoTrue, so its isolated fixture adds those same lifecycle columns; this never modifies production Auth schema. Existing older desktop binaries do not acquire the new guard until upgraded. A missing managed Auth prerequisite fails authorization; do not remove the account-state check to proceed.
