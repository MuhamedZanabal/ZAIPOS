# Catalogue and stock exports

Settings → Data Management exports either a spreadsheet CSV or a versioned JSON snapshot. A current same-branch manager, admin or owner is required; cashier, wrong-branch, cross-tenant, inactive/banned/deleted account and revoked-role requests fail closed. Apply the migration before upgrading the client.

The server returns one scalar `zaipos.business-export.v1` JSON document from a stable PostgreSQL statement snapshot. This avoids a REST row limit silently clipping table selections and avoids drift between separately paginated requests. Records are sorted by stable IDs, and barcodes by stored order/ID. The envelope identifies business, selected branch, domain, UTC export timestamp and record count. The client checks scope and count before download. Repeated exports of unchanged data have identical records, with a new export timestamp.

Catalogue scope is the selected tenant's shared base catalogue: product identity, name, SKU, description, category identity/name, base selling and cost fils, VAT rate, minimum stock, status, unit, type and barcode records. It is not branch/channel override pricing or historical financial evidence. Inventory scope is current aggregate stock in the selected tenant and branch, with product/center identities, names and exact quantity. It does not contain lot-level balances, movements or stocktake history. Those authoritative records remain in the verified database backup.

Integer fils and numeric quantities are exported as strings. CSV decimal price/cost displays are derived with integer arithmetic. JSON preserves selected string values, Unicode, newlines, barcode arrays and nulls without spreadsheet transformations. CSV applies formula protection and flattens barcode arrays with `|`; use JSON when exact field/array fidelity matters. JSON is an interchange snapshot for outside tools, not an application restore/import command.

Each inventory CSV includes a new count reference and explicit tenant/branch/center IDs. Keep the original reference for retries; new physical counts require new references. Import rejects supplied destination IDs that disagree with the selection, even when two centers share a name. Manual count files still require an explicit count reference. See INVENTORY_COUNT_RETRY.md.

The interactive snapshot is bounded to 50,000 records and 32 MiB of record JSON. Exceeding either limit raises an error and produces no download. Empty snapshots are available as JSON. For larger datasets, the database operator must use a scoped consistent database export in an approved environment; never raise a REST cap and assume that proves completeness. This limit is not a measured production performance guarantee. The UI/database contracts exercise 1,501 records, and CI records elapsed fixture time.

Exported files contain commercial information. Save them only to an approved restricted location, use encryption when transferring or retaining sensitive files, and apply the business retention policy. The application does not log or persist a copy of exported records. A successful browser download dispatch does not prove the operator's storage medium is durable. Database backup/restore is the disaster-recovery mechanism; these snapshots are not substitutes.

Evidence: two RED UI assertions used a 1,000-row API-cap simulation against a 1,501-record source and an authorization denial. The initial PostgreSQL contract fails on the absent authoritative export RPC. Full-schema tests cover 1,501 products/stock records, string fils/quantities, Unicode/barcode fidelity, deterministic records, read-only fingerprints, scope and role denial. Client tests reject count/scope/money-type mismatch and verify lossless JSON download bytes.

Remaining export scope: customer/supplier statements, historical transactional/accounting exports and large-dataset streaming need their own domain audit. Do not describe this change as complete portability of every ZAIPOS domain.
