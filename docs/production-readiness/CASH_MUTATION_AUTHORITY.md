# Cash movement authority

The full-schema authenticated-role contract reproduced two defects in the legacy cash movement RPC: a cashier from another branch in the same tenant could record cash, and sub-fils inputs were accepted and rounded. Direct table mutations were already denied in the tested PostgreSQL environment; existing permissive write policies nevertheless depended on deployment grants and are removed explicitly.

Cash-session totals and movement rows are now read-only to application roles. Movements require the server command, a current authorized branch role, active branch/account/employee state, a positive exact-fils amount and a reason. The command locks the cash session before checking its open state and holds that lock through movement insertion, exact counter updates and immutable audit evidence. A concurrent close waits and includes the committed movement. Failed commands roll back every effect. Existing movement rows cannot be updated or deleted; corrections require a separate explained movement, preserving history.

The UI validates typed decimal text without floating-point rounding before sending canonical three-decimal text. Invalid sub-fils input rejects, and authorization/network errors restore the form controls instead of leaving them permanently busy. Manager/cashier branch roles retain their existing command access; these checks do not establish physical custody of a drawer.

Verification includes actual authenticated PostgreSQL role calls, cross-branch denial, direct write denial, one-fils precision, audited movement evidence, mutation/deletion denial, and a controlled insertion-versus-close race. The final close must include the movement with zero discrepancy. CI and release quality gates run the contract. Existing checkout/refund/void/delivery commands continue updating counters through their authorized transactions.

Remaining P0/P1 cash work: the legacy command has no operation ID and must not be blindly retried after an ambiguous response. Durable command identity/replay for cash in/out and session opening/closing is the next repository task. Investigate historical movement/session/audit evidence before retrying an uncertain legacy command. Customer-credit and supplier settlements still need explicit receiving/paying-till integration where physical cash is handled. This change does not certify all cash lifecycle workflows.

Deployment: back up, apply the migration, upgrade the UI, and test cashier/manager operation in each authorized branch. Historical records are not rewritten. Supabase-managed Auth lifecycle migrations are required, as documented for native manager authorization. Older clients may submit amounts that were already rounded locally; upgrading them is necessary to preserve typed-input fidelity.
